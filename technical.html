Schema is the single source of truth

const userSchema = new Schema({
  email: { type: String, required: true },
  role:  { type: String,
           enum: ["client", "designer"] },
})

export type UserDoc =
  InferSchemaType<typeof userSchema>
// → { email: string, role: "client"|"designer" }
When the schema changes, the TypeScript type updates automatically. TypeScript then flags every caller that breaks — no manual type syncing needed.

Frontend typed API client

// One generic fetch wrapper
async function api<T>(path: string): Promise<T> {
  const res = await fetch(BASE + path, {
    headers: { Authorization: `Bearer ${token}` }
  })
  return res.json() as Promise<T>
}

// Fully typed — no any, no casting
const user = await api<AuthUser>("/auth/me")
Because the type flows all the way from the DB schema to the React consumer, a renamed field in the schema becomes a TypeScript error in the component — caught at compile time, not at runtime.

JWT payload — minimal

jwt.sign(
  { sub: String(user._id),
    role: user.role },
  JWT_ACCESS_SECRET,
  { expiresIn: "7d" }
)
  • Only sub (userId) and role in payload
  • Minimal exposure if token is intercepted

Key decisions explained

  • bcrypt cost 10 — slow enough to resist brute force, fast enough for UX (takes ~100ms)
  • Email lowercased on save — prevents duplicate accounts with different casing
  • Role chosen at registration — no admin self-registration, not offered in the UI form
  • 7-day expiry — balance between security and not forcing re-login constantly
The JWT payload carries the role so the frontend knows which dashboard to render immediately — but the backend re-fetches the role from MongoDB on every request to prevent stale data. See slide 5.

Why the DB re-fetch?

A JWT is self-contained and valid until expiry — jwt.verify() doesn't touch the database. That means if a user is deleted or their role changes, the token would still pass verification for the remaining 7 days. Re-fetching from MongoDB makes the check live — deleted users are blocked instantly.

TypeScript augmentation

Express's Request type doesn't have a user property. The project extends it:

// types/express-augment.ts
declare global {
  namespace Express {
    interface Request {
      user?: { id: string; role: AppUserRole }
    }
  }
}

Every controller reads req.user with full type safety — TypeScript knows the shape.

Only role is selected from the DB (.select("role")) — a targeted query, not fetching the entire user document on every request.

What a Zod schema looks like

export const createBriefBody = z.object({
  title:       z.string().min(1),
  designType:  z.enum(["logo", "poster",
                 "branding", "social-media", "website"]),
  deadline:    z.coerce.date(),  // "2025-06-01" → Date
  budget:      z.number().optional(),
})

// .partial() reuses the schema for PATCH
export const updateBriefBody = createBriefBody.partial()

What validateBody actually does

  • Rejects bad data early — controller never receives malformed input
  • Coerces types — z.coerce.date() converts ISO strings to real Date objects
  • Applies defaults — optional fields with defaults are filled in automatically
  • Writes clean data back — req.body = result.data so controllers always have safe input
createBriefBody.partial() makes every field optional — one schema definition powers both the POST (all required) and the PATCH (all optional). No duplication.

Design choices

Why sub-router pattern?

  • requireProjectAccess runs once — all 7 sub-routes are protected automatically, no per-route repetition
  • Middleware order is explicit — .use() before the routes means it always runs first
  • Clean separation — top-level router handles list/create, sub-router handles per-resource operations

Access is granted if the user is the project owner OR has a ProjectMember record. Valid JWT + correct role is not enough on its own.

asyncHandler — no try/catch in controllers

Wraps every async controller: Promise.resolve(fn()).catch(next) — uncaught rejections go to errorHandler automatically. throw new ApiError(403, "Forbidden") becomes a proper JSON response.

Why the loading check matters

On first page load, AuthProvider calls /auth/me to restore the session from a stored token. Until that request resolves, user is null — even for a logged-in user. Without the loading check, every logged-in user would see a flash redirect to /login before the session is restored.

state.from — return to where you were

When an unauthenticated user hits a protected URL, ProtectedRoute saves their intended location in state.from. After login, LoginForm reads this state and redirects them back — instead of always dumping them on the dashboard.

homeForRole

If a designer navigates to /client/dashboard, RoleRoute redirects to homeForRole("designer") = /designer/dashboard. No blank error page — just the right dashboard for their role.

Security

Five layers — applied in order, each with a specific job

12 / 15
1
Helmet
Sets 11 HTTP security headers in one call — X-Content-Type-Options, X-Frame-Options, HSTS, Referrer-Policy and more. Runs before anything else touches the request.
2
CORS whitelist
Origin checked against a set built from CORS_ORIGIN env variable. No-origin requests (curl, server-to-server) pass through. Cross-origin requests from unlisted domains are silently rejected. Preflight cached for 24h.
3
Rate limiters
API routes: 600 requests / 15 min per IP. Auth routes (login/register): 20 requests / 15 min — much stricter to prevent credential brute forcing.
4
NoSQL Sanitizer
Runs after express.json() — strips $ and . keys from request bodies. Blocks MongoDB operator injection attacks like {'{"email": {"$gt": ""}}'} that bypass authentication.
5
Zod per-route
Last line of defence — each route that accepts a body has a Zod schema. Malformed requests are rejected with a 400 and a clear error message before the controller runs any business logic.
The order matters: Helmet and CORS run on the raw request. Rate limiter rejects before parsing. NoSQL sanitizer needs a parsed body. Zod runs per-route after all global middleware.

AuthContext — how auth state reaches every component

AuthProvider → consumers
AuthProvider{ user, loading, login, logout, register }
ProtectedRoutereads: user, loading

useAuth()any component

Session restored on mount

// On mount: check if stored token still works
useEffect(() => {
  if (!token) { setLoading(false); return }
  api<AuthUser>("/auth/me")
    .then(setUser)
    .catch(() => {
      localStorage.removeItem("creativehub_token")
      setToken(null)  // token expired or revoked
    })
    .finally(() => setLoading(false))
}, [token])

Why useCallback on login and logout?

The context value object is memoised with useMemo. Without useCallback, login and logout would be new function references on every render — making the useMemo comparison always fail and causing every context consumer to re-render.

  • useCallback(login) — stable reference, only changes if dependencies change
  • useMemo(value) — context object only re-created when user, token, or loading changes

useAuth — the consumer hook

Components never import AuthContext directly. They call useAuth(), which throws a descriptive error if used outside AuthProvider — much better than a silent undefined crash.

const { user, login, logout } = useAuth()
// Works in any component inside <AuthProvider>
The JWT token is stored in localStorage under a fixed key. If it fails the /auth/me check (expired, revoked, tampered), it is cleared automatically and the user is treated as logged out.
Design Patterns

Single Responsibility — components do one thing, hooks own the logic

14 / 15
Without SRP — one large component
  • Sidebar knows the user's role and renders different links conditionally
  • Dashboard page fetches data, formats numbers, handles empty states, and renders the layout
  • A nav item change requires editing the Sidebar and every place that renders it
  • Components can't be reused elsewhere because they carry too much context
With SRP — as built in Creative Hub
  • Sidebar just renders items — useDashboardNav() decides what they are
  • MetricCard displays a value and label — it knows nothing about projects or briefs
  • StatusPill colours a status string — one component for all status values across the app
  • Adding a nav item means editing buildNavItems(), not touching any component

The hook / component split

useDashboardNav()
→ knows which links exist for each role
Sidebar
→ maps over items, renders NavLink for each
useAuth()
→ holds user state and auth functions
LoginForm
→ calls login(), shows error if it throws
useRoleArea()
→ derives current area from URL
DashboardLayout
→ renders Sidebar + Outlet, nothing else
This structure mirrors what Vue calls Composables, what React calls custom hooks — extract the "what" into a hook, keep the "how it looks" in the component. Follows the SRP requirement from the project spec directly.
Summary

The architectural decisions that hold it all together

15 / 15
1

TypeScript end-to-end — InferSchemaType on Mongoose schemas. Types flow from DB schema → API response → React hook → component. One source of truth.

2

Layered auth — bcrypt on passwords, JWT for stateless tokens, requireAuth re-checks the database on every call, requireProjectAccess enforces workspace membership per project.

3

Zod before every controller — validateBody middleware rejects bad input early. req.body is always clean, coerced, and typed. .partial() reuses schemas for PATCH routes.

4

5-layer security — Helmet headers, CORS whitelist, two rate limiters (API 600/15m, auth 20/15m), NoSQL sanitizer, Zod per-route. Order is deliberate.

5

Auto project creation — brief submission instantly creates a draft project + 4 Kanban columns + client as lead. Designer acceptance moves it to in_progress. No admin step.

6

SRP throughout — hooks own logic, components own rendering, context owns shared state. Sub-router pattern on the backend mirrors this: one middleware, many routes.
